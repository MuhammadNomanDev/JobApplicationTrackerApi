## Q&A

### 1. Why did you deploy manually instead of using the Bicep template?
The subscription is Pakistan-billed with zero free-tier quota in every region
I tried (UK South, UK West, West Europe, UAE North). Bicep/CLI deployment
kept failing on quota. The portal succeeded in West US 3 — manual creation
worked where automation couldn't. The Bicep file is kept as future-state IaC
documentation, reconciled to West US 3, not a claim that it provisioned the
live environment.

### 2. What was the exit code 139 and why did the container segfault?
Exit 139 = 128 + 11 = SIGSEGV (segmentation fault). The Docker logs showed
the container crashing 3–4 seconds after startup during the initial
deployment (11:34–11:37 UTC). This is a native-level crash, not a .NET
exception — the process died before producing any application logs. It
stopped occurring after the container configuration was corrected, suggesting
it was related to the initial misconfiguration rather than a bad image.

### 3. Why did the app return 503 after the segfaults stopped?
The .NET app was running (we saw DataProtection and Service Bus logs) but
App Service couldn't route traffic to it. The Dockerfile `EXPOSE`s port 8080
(.NET 10's default), but App Service expects port 80 by default. The fix was
two app settings: `WEBSITES_PORT=80` (tells App Service which port to route
to) and `ASPNETCORE_URLS=http://+:80` (tells .NET which port to listen on).

### 4. Why couldn't you see the "Now listening on..." log message?
Serilog is configured with `.MinimumLevel.Override("Microsoft", Warning)`.
The "Now listening" message comes from `Microsoft.Hosting.Lifetime` at
Information level, so it was filtered out. We saw our own INF logs (like the
Service Bus "disabled" message) but not Microsoft's. This made it look like
the app wasn't finishing startup when it actually was.

### 5. Why use OIDC instead of AZURE_CREDENTIALS for GitHub Actions?
`AZURE_CREDENTIALS` is a long-lived service principal secret stored in GitHub.
If leaked, it grants access until manually rotated. OIDC mints a short-lived
token per workflow run — GitHub proves its identity to Azure via a federated
credential, Azure issues a token valid only for that run. No stored secret to
leak, rotate, or expire. The workflow needs `permissions: id-token: write`
to request the OIDC token.

### 6. What is a federated credential and how does the trust work?
A federated credential on the Entra app says: "Trust OIDC tokens from this
GitHub repo + branch." When the workflow runs, GitHub mints a JWT asserting
`repo:MuhammadNomanDev/JobApplicationTrackerApi:ref:refs/heads/main`.
Azure validates the JWT signature against GitHub's OIDC issuer, checks the
subject matches the federated credential, and issues an Azure access token.
The Entra app only has Contributor on `rg-jobtracker`, so the token can't
touch anything outside that resource group.

### 7. Why did the SQL Query Editor fail with "Deny public network access"?
The SQL server had "Deny public network access" set to Yes, blocking all
public connections including the portal's Query Editor. Fixed by setting it
to Allow and enabling "Allow Azure services and resources to access this
server" (the Web App needs this to connect). For production, you'd lock this
down with VNet integration or specific firewall rules instead.

### 8. Why run migrations via SQL script instead of `dotnet ef database update`?
The database was empty (no tables) and the app doesn't auto-migrate on
startup. Running `dotnet ef` requires the EF tooling and a working
DbContext design-time factory — the tool couldn't construct our DbContext
in this environment. The migration was a single `InitialCreate` with 4
tables, so I translated the `Up()` method to T-SQL manually, including the
`__EFMigrationsHistory` table and the migration record insert. For future
migrations, adding `dbContext.Database.Migrate()` to Program.cs (or fixing
the design-time factory) would be cleaner.

### 9. What does `WEBSITES_PORT` actually do?
It's an App Service app setting that tells the platform which port inside
the container to route HTTP traffic to. Without it, App Service defaults to
port 80. If your container listens on a different port (like .NET's default
8080), you must set `WEBSITES_PORT` to match, AND ensure the app actually
listens on that port (via `ASPNETCORE_URLS` or the framework default).

### 10. How would you make this production-ready?
- **Database:** Enable auto-migration or run migrations in CI/CD; set up
  automated backups; use private endpoints instead of public access.
- **Secrets:** Move JWT key and connection string to Azure Key Vault with
  managed identity (no secrets in app settings).
- **Observability:** Ship Serilog logs to Application Insights; add
  alerting on health check failures and 5xx rates.
- **Scaling:** Configure autoscale rules; use deployment slots for
  zero-downtime releases.
- **Security:** Enable HTTPS-only; add WAF in front; rotate the GHCR token.

1. Go to GitHub → your repo → **Actions** → find the latest workflow run on

4. Go to `rg-jobtracker` → **Access control (IAM)** → **Role assignments**.
   Confirm `jobtracker-github-actions` has Contributor. What could it do
   with this role that it couldn't do with Reader?

   GitHub secrets, what could they do? How is this better or worse than

token → Azure validates against federated credential → short-lived access
token scoped to rg-jobtracker → container deployed — without looking at
notes.
