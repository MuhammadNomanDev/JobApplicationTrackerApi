# Learning note: P0 — Foundations and GitHub clean-up

## 1. What was built and why
P0 removes the red flags a hiring manager spots in the first 30 seconds on a GitHub profile, and installs the automation every later project depends on. A `.mailmap` maps two commits authored with a former employer's email to Noman's name and noreply address for display — without rewriting published history, which would break every existing clone. The CI pipeline (`ci-cd.yml`) now runs the integration tests on every push and PR, not just unit tests; they needed test-only `Jwt__*` environment variables because `Program.cs` reads the JWT signing key at startup and CI has no user-secrets. Container publishing moved from Docker Hub to the GitHub Container Registry (GHCR): no extra credentials to manage, images live next to the code, and the `deploy` job's image reference was updated to match. Dependabot (weekly NuGet + Actions updates) and CodeQL (static analysis on push, PR and weekly) were added so vulnerabilities and stale dependencies surface as PRs instead of surprises. Finally, the profile README (`MuhammadNomanDev/MuhammadNomanDev`) now states the positioning line, availability and what Noman is good at, with project rows hidden until each flagship is live and demoed. Nothing here changes application code — it is all hygiene, and that is the point: a clean, automated, trustworthy-looking GitHub is the foundation the portfolio builds on.

## 2. Code walkthrough
- **`.github/workflows/ci-cd.yml`** — the whole pipeline. The `build` job restores, builds, runs unit tests, then the new **Run Integration Tests** step (with dummy `Jwt__*` env vars so the API can boot). The `docker` job (main branch only) logs into GHCR with `GITHUB_TOKEN` and pushes `:latest` + `:${{ github.sha }}` tags. The `deploy` job is untouched except the `images:` reference, which now points at GHCR.
- **`.mailmap`** — one line mapping `muhammad.noman@khi.efrotech.com` to Noman's name + noreply address. Affects `git log`/`blame` display only; commit SHAs are unchanged.
- **`.github/dependabot.yml`** — weekly checks for NuGet and GitHub Actions updates, max 5 open PRs per ecosystem so it never spams.
- **`.github/workflows/codeql.yml`** — builds the solution and runs CodeQL's C# security queries; findings appear under the repo's Security tab.
- **`docs/learning/p0.md`** — this file: the interview-defence pack for the milestone.

## 3. Ten likely interview questions
1. **What does `.mailmap` do, and why didn't you rewrite history?** It remaps author name/email for display in `git log`/`blame` without changing commit SHAs. Rewriting published history (`filter-branch`/`filter-repo`) invalidates every existing clone and breaks the "don't rewrite published history" rule; mailmap is the safe, standard fix.
2. **Why do the integration tests need `Jwt__Key`/`Jwt__Issuer`/`Jwt__Audience` in CI?** `Program.cs` reads the `Jwt` section at startup to build the token-validation key. Locally that comes from user-secrets; CI has none, so the workflow injects dummy values via env vars (which the config binder maps through the `__` separator).
3. **These integration tests don't touch a database — what do they actually prove?** They boot the real app via `WebApplicationFactory` and prove the request pipeline works: routing, model validation (400s), auth middleware (401s). They catch startup crashes and pipeline misconfiguration, which unit tests can't.
4. **Why move the image from Docker Hub to GHCR?** No separate Docker Hub account/secrets to manage; auth uses the built-in `GITHUB_TOKEN`; images are versioned and visible next to the repo; and GHCR has a generous free tier for public repos.
5. **Why does the docker job need `permissions: packages: write`?** The default `GITHUB_TOKEN` is read-only for packages. Pushing an image is a write, so the job must explicitly request it — least-privilege in action.
6. **Why is the GHCR path lowercase (`muhammadnomandev`) when the username isn't?** Container registries require lowercase repository paths (Docker distribution spec). Uppercase would fail at push time.
7. **What does Dependabot do, and would you auto-merge its PRs?** It opens PRs for outdated/vulnerable dependencies on a schedule. I would not blindly auto-merge: minor/patch maybe with green CI, but major bumps (especially the commercially-licensed ones flagged in our licensing ADR) need a human review.
8. **What does CodeQL catch that the C# compiler doesn't?** The compiler catches type errors; CodeQL does data-flow analysis for security issues — SQL injection paths, unsanitised input reaching sensitive sinks, weak crypto, SSRF patterns. Different layer entirely.
9. **Why does `docker` only run on `main` while `build` runs on PRs too?** Building and testing every PR catches breakage early with zero side effects. Pushing images is a side effect (publishes `:latest`); doing it per-PR would spam the registry and could publish broken images.
10. **The deploy job still targets the old Azure setup — why leave it?** P0 is hygiene, not re-architecture. The image reference was kept consistent so nothing silently breaks, and deployment is properly reworked with OIDC + Bicep in P1/M2.

## 6. Postscript: the unit tests were already broken (fixed in this PR)
CI's first full run exposed failing unit tests on `main` — they were committed broken, not broken by P0. Two distinct bugs:
1. **Mocking EF Core extension methods (3 tests).** The Auth tests called `_mockContext.Setup(x => x.Users.FirstOrDefaultAsync(...))` / `AnyAsync(...)`. Those are static extension methods on `EntityFrameworkQueryableExtensions`, not virtual members of `DbSet<User>`, so Moq throws `NotSupportedException: ... may not be used in setup / verification expressions`. The fix mocks the `DbSet<User>` itself with an in-memory async query provider (`tests/JobApplicationTrackerAPI.UnitTests/Helpers/MockDbSetHelper.cs`, the documented EF Core testing pattern), so the real extension methods execute against the supplied test data.
2. **Unset mock returning null (1 test).** The Create test never set up `IAppDbContext.JobApplications`, so the mock returned null and the handler's `AddAsync` threw `NullReferenceException`. The fix sets up a `Mock<DbSet<JobApplication>>` in the test constructor.

### Second bug found by the same CI run: wrong ValidationException type (3 tests)
Once the mocks were fixed, the tests revealed a deeper inconsistency: the Auth handlers threw `System.ComponentModel.DataAnnotations.ValidationException`, but the tests (and the rest of the codebase) expect `FluentValidation.ValidationException`. These are unrelated types. Worse, the `GlobalExceptionHandler` middleware only maps the FluentValidation variant to HTTP 400 — so a real invalid-login or duplicate-registration request was returning **500 Internal Server Error** in production. The fix changes the three Auth handlers (`Login`, `Register`, `RefreshToken`) to `using FluentValidation;`, aligning them with the middleware and the MediatR `ValidationBehavior`. One-line-per-file change, one real bug fixed, three tests green.

### Third fix: integration tests used a fake token and needed a database (4 tests)
The first CI run of the integration tests failed all four `JobApplicationEndpointTests`: they sent `Authorization: Bearer fake-token`, which the JWT middleware rejects with 401 before any handler runs. The fix generates a real JWT in the test via the app's own `IJwtTokenGenerator` (resolved from the factory's service provider), so the token validates against the same settings the API booted with. The invalid-request test then passes (400 from the validation pipeline, no database needed). The three not-found tests are `[Fact(Skip = ...)]` for now: with no database in CI, the handler's query would fail with a connection error instead of returning 404. They will be re-enabled in P1/M1 when integration tests move to Testcontainers SQL Server. Skipped with a reason beats deleted: the intent stays visible in test output.
